# 个人微信小程序发布指南

> 适用前提：中国大陆居民，以个人主体注册，没有营业执照。
>
> 规则核对日期：2026-11-24。类目页面最近编辑于 2026-11-16；个人虚拟支付页面最近编辑于 2026-11-03；小程序接入指南最近编辑于 2026-07-28。
>
> 本文用于产品规划，不替代微信公众平台的实际审核结果，也不替代法律、税务或行业准入意见。

## 1. 先回答两个问题

### 1.1 没有营业执照能申请几个？

**最多 5 个。** 腾讯客服的《小程序主体上限》明确写明：企业、政府、媒体、其他组织主体可注册 50 个，个体户和个人类型主体可注册 5 个。

但“最多 5 个”只是账号额度，不代表可以随意拆成 5 个。微信运营规范明确禁止重复注册、提交 2 个及以上页面、内容、功能相同或同质化严重的小程序。

因此：

| 情况 | 建议 |
|---|---|
| 同一个 OPC 品牌下的应用、案例、业务介绍 | 先放在 1 个小程序内 |
| 用户群、核心功能、使用场景明显不同 | 才考虑拆分成第 2 个 |
| 只是同一套内容换名称、换图标 | 不建议拆分，可能因同质化被拒 |
| 需要交易、商城、付费课程、复杂经营能力 | 优先评估个体工商户或企业主体，而不是继续拆个人小程序 |

**推荐：先做 1 个，保留额度，验证需求和审核路径。**

### 1.2 个人主体有哪些类目？

截至 2026-11-24，个人主体开放以下 **8 个一级类目**。详细资质和范围以官方类目页面及提交审核时的后台提示为准。

| 一级类目 | 开放内容 | 关键边界 |
|---|---|---|
| 物流服务 | 查件、装卸搬运 | 查件不包含寄件、收件 |
| 教育服务 | 教育信息展示 | 不支持教育视频播放/直播、课程销售 |
| 生活服务 | 丽人服务、家政服务、婚庆服务 | 丽人不含医疗美容、推拿、洗浴等未开放业务 |
| 餐饮服务 | 餐厅排队 | 不含线上点餐、外卖 |
| 旅游服务 | 出境 WiFi | 不含境外流量、话费充值 |
| 工具 | 记账、日历、天气、办公、图片处理、计算器、报价/比价、信息查询、预约/报名、健康管理、备忘录 | 记账不含用户自定义生成内容记录及分享；备忘录不含原创内容传播及公开访问 |
| 商业服务 | 律师、企业管理、会展服务、摄影/扩印、公关/推广/市场调查、环保回收/废品回收 | “律师”需要《律师执业资格证》 |
| 体育 | 体育培训、在线健身 | 不得扩展为未申报的课程销售或经营服务 |

官方来源：[微信小程序开放的服务类目](https://developers.weixin.qq.com/miniprogram/product/material/#个人主体小程序开放的服务类目)。

## 2. 主体与能力：先定边界，再写代码

### 2.1 个人主体的定位

个人主体更适合：

- 工具：查询、计算、记录、日历、图片处理、预约报名等。
- 个人作品与项目展示。
- 应用能力介绍、使用说明、案例介绍。
- 非交易闭环的业务介绍与联系入口。
- 符合个人开放类目的轻量服务。

个人主体不适合直接照搬企业级方案：

- 商品商城、实物交易、外卖、多商户平台。
- 付费课程、课程销售、教育培训平台。
- 资讯分发、UGC 社区、陌生人社交、直播等未向个人主体开放的类目。
- 金融、医疗、政务、新闻等需要相应主体或资质的服务。
- AI 生成、深度合成、内容平台等需要单独类目和资质的功能。

**类目不是标签，而是功能边界。** 实际页面、接口、支付、内容和服务都必须与所选类目一致，不能先选一个宽松类目，再在审核后增加未申报功能。

### 2.2 普通微信支付与个人虚拟支付不是一回事

截至规则核对日，需要区分两种能力：

#### 普通微信支付 / 商户收款

- 小程序接入指南写明：已认证的小程序可申请微信支付。
- 同一页面同时写明：个人类型账号暂不支持微信认证。
- 因此，个人主体不能按企业/个体户的普通商户收款路径规划商城、实物交易或企业级服务闭环。

#### 个人虚拟支付

微信在 2026 年新增了“虚拟支付：个人”文档，向符合条件的个人主体开放虚拟支付。其当前条件包括：

- 小程序主体为个人，开发者持有居民身份证。
- 服务类目含“工具”。
- 已完成小程序认证、备案。
- 月支付限额 10 万元。
- Android 等终端技术服务费 1%，iOS 为 12% Apple 佣金。
- 不支持需办理电信业务相关资质的服务，例如电子邮件、语音信箱、储存转发、信息发布平台、信息搜索查询等。

需要特别注意：**“工具”类目下有“信息查询”，而个人虚拟支付又明确不支持“信息搜索查询”等服务。** 不能因为类目名称里都有“工具”，就默认所有工具类应用都能收费。

此外，2026-11 的个人虚拟支付文档要求“已完成小程序认证”，但 2026-07 的小程序接入指南仍写“个人类型账号暂不支持微信认证”。这属于官方文档之间的状态不一致。**是否实际可用，必须以注册账号后台是否出现认证、备案和虚拟支付入口为准；无法确认时先按无支付能力设计。**

产品建议：

- 第一版不依赖支付也能完整使用。
- 如需收费，先确认个人虚拟支付的实际开通资格、类目范围和业务类型。
- 需要普通商户收款、实物商品交易或完整企业经营能力时，优先考虑个体工商户主体。

## 3. 个人 OPC 应该做成什么样

### 3.1 推荐定位

建议定位为：

> **个人 OPC 的应用工作台、作品集与业务介绍入口。**

它回答三个问题：

1. 你是谁，擅长什么？
2. 你做过哪些应用、项目和成果？
3. 你能提供哪些业务，如何联系和咨询？

### 3.2 不建议定位

不建议做成：

- “小程序应用市场”：集中推荐、排行、跳转大量其他小程序。
- “所有 App 下载中心”：通过集中下载、推荐、排行为其他应用导流。
- 伪装的商城：不展示价格，但引导到小程序外付款。
- 多功能大杂烩：首页堆满与主体、类目和实际服务无关的功能。

微信运营规范明确限制对小程序、小游戏或其他 App 进行推荐、推广、排行或集中设立跳转、添加平台服务。个人主体也不能随意展示或推荐其他小程序或公众号。

因此，“展示你的所有应用”应优先理解为：

- 展示你拥有的应用名称、定位、功能、截图、案例和成果。
- 如果应用是本小程序内部的模块，可以在小程序内直接使用。
- 如果应用是独立产品，先展示项目介绍；外链、打开 App、跳转其他小程序等能力必须单独核对类目、域名和平台规则。

### 3.3 推荐信息架构

首版保持 4 个主要页面即可。

| 页面 | 内容 | 主要动作 |
|---|---|---|
| 首页 | 个人 OPC 一句话定位、代表应用、核心能力、最近更新 | 查看代表应用 / 浏览业务 |
| 应用 | 按工具、项目、实验、企业服务分组；搜索或筛选 | 查看应用详情 |
| 业务 | 服务类型、适合场景、交付流程、案例、FAQ | 预约或联系咨询 |
| 关于 | 个人介绍、经历、作品原则、联系方式、隐私说明 | 联系 / 查看项目来源 |

应用详情页建议包含：

- 应用名称与一句话价值。
- 解决什么问题，适合谁。
- 核心功能 3—6 条。
- 真实截图或演示。
- 当前状态：可用、内测、维护中、已归档。
- 更新日期和版本说明。
- 合规前提下的项目入口或使用说明。

业务详情页建议包含：

- 业务范围与不适合的范围。
- 服务流程和所需材料。
- 交付物与时间预期。
- 案例或作品链接。
- 联系与咨询方式。
- 如暂不支持线上收款，明确说明通过合规渠道沟通，不隐藏交易意图。

## 4. 类目怎么选

### 4.1 按真实主功能选，不按名字选

可以根据最终产品形态考虑：

| 产品形态 | 可优先评估的类目 | 注意 |
|---|---|---|
| 应用目录、应用信息检索 | 工具—信息查询 | 若本质是信息平台或涉及大量第三方应用导流，需重新评估是否适合个人主体 |
| 个人办公工具、项目工作台 | 工具—办公 | 必须有真实工具能力，不能只是空壳展示 |
| 自有业务介绍、门店信息展示、轻量管理 | 商业服务—企业管理 | 仅适用于真实企业管理、办公管理或门店信息展示，不是通用“万能类目” |
| 预约、报名 | 工具—预约/报名 | 不自动等于可以收款 |
| 摄影作品与服务介绍 | 商业服务—摄影/扩印 | 若同时售卖套餐，需要评估交易和主体限制 |
| 教育信息展示 | 教育服务—教育信息展示 | 不能播放教育视频、直播或销售课程 |

**最稳妥的做法：先画出页面和功能清单，再逐项对应官方类目的“类目适用范围”；无法覆盖的功能删除或改用合适主体。**

### 4.2 不建议为了过审选择近似类目

平台会以最终提交代码审核版本为准。隐藏页面、暂未上线的收费入口、未申报的 AI 生成、社区发帖、视频课程等，都可能被认定为类目不符或隐藏类目。

## 5. 设计最佳实践

微信设计指南强调四点：**友好礼貌、清晰明确、便捷优雅、统一稳定**。落实到个人 OPC 小程序，可以采用以下做法。

### 5.1 首页

- 第一屏说清楚“你是谁 + 提供什么 + 下一步做什么”。
- 只保留一个主行动按钮，例如“查看应用”或“咨询业务”。
- 展示 2—3 个代表项目，不要一次铺开所有内容。
- 用真实截图和可验证成果，少用空泛口号。
- 避免自动播放视频、轮播轰炸、强制分享和无关弹窗。

### 5.2 应用列表

- 按使用场景分组，而不是按技术栈分组。
- 每张卡片只保留：图标、名称、一句话价值、状态。
- 支持搜索、筛选或分组中的一种即可，功能少时不必强行增加筛选。
- 明确“可用 / 内测 / 维护中 / 已归档”，避免用户点击后预期落差。
- 列表为空、加载失败、详情失效时提供清晰反馈。

### 5.3 业务页面

- 先讲适合谁，再讲交付流程。
- 明确不能提供的服务，减少无效咨询。
- 价格、周期、交付物如暂未确定，不要编造。
- 支付不可用时，不要用“打赏”“赞助”等名义变相收费。
- 联系入口保持可见，但不要频繁索取手机号、位置、相册等权限。

### 5.4 交互与视觉

- 使用微信原生组件和常见交互，降低学习成本。
- 导航明确，返回路径自然；弹层可关闭。
- 点击热区足够大，文字对比清晰，支持系统字体放大。
- 表单减少输入，错误提示靠近字段，并说明如何修正。
- 图片按移动端尺寸压缩，首屏避免加载大图和视频。
- 保持图标、圆角、色彩、间距一致，不模仿微信官方或国家机关视觉。
- 深色模式、无障碍、弱网、长文本和大屏适配按实际用户需求逐步完善。

官方设计来源：[微信小程序设计指南](https://developers.weixin.qq.com/miniprogram/design/index.html)。

## 6. 上架前检查清单

### 6.1 主体与账号

- [ ] 确认个人身份信息真实、有效，且符合注册条件。
- [ ] 确认当前个人主体注册数量未超过 5 个。
- [ ] 每个小程序使用独立邮箱；邮箱不能与已有公众平台、开放平台等账号冲突。
- [ ] 管理员微信真实有效，账号和邮箱由本人控制。
- [ ] 不借用、租用他人营业执照或资质。

### 6.2 类目与功能

- [ ] 每个页面和核心功能都能对应到已申报类目。
- [ ] 没有隐藏类目、隐藏页面、未申报收费入口。
- [ ] 没有集中推荐、排行、互推其他小程序或 App。
- [ ] 没有未经允许的 UGC、社区、资讯、直播、课程销售或 AI 生成功能。
- [ ] 首页能直接看到核心功能，不是只有介绍页或空壳页面。

### 6.3 内容与素材

- [ ] 名称、头像、简介与实际功能一致。
- [ ] 名称不侵犯他人商标、品牌、姓名或肖像权。
- [ ] 不使用“微信官方”“腾讯官方”等误导性表述。
- [ ] 截图、案例、图标、字体、代码和第三方素材有合法使用权。
- [ ] 页面没有虚假宣传、绝对化用语、诱导分享或网赚信息。

### 6.4 隐私与数据

- [ ] 配置《小程序用户隐私保护指引》，声明实际收集的字段。
- [ ] 只在用户使用时申请必要权限，并说明用途。
- [ ] 不强制索取与核心功能无关的个人信息。
- [ ] 不向其他用户公开微信号、手机号、邮箱等个人信息。
- [ ] 如收集咨询信息，提供删除、更正和联系方式。
- [ ] AppSecret、支付密钥、管理员凭证不写入前端代码或提交到仓库。

### 6.5 备案、认证与审核

- [ ] 按微信要求完成小程序备案。
- [ ] 如依赖认证或虚拟支付，先在后台确认入口和实际资格。
- [ ] 准备真实、可完成的测试流程；需要登录时提供审核测试账号。
- [ ] 重要业务页面配置正确的类目和标签，页面组数按官方要求填写。
- [ ] 在真机上检查首页、列表、详情、返回、弱网和空状态。
- [ ] 审核通过后手动发布，并再次检查线上版本。

## 7. 主体升级与长期规划

不要把“先用个人主体，之后再升级”当作没有成本的方案。

腾讯客服的《小程序主体变更条件》目前写明：

- 小程序必须是已成功注册的小程序账号。
- 境外小程序账号不支持主体变更。
- **目标主体不支持为个人类型。**
- 目标主体不能与原主体相同。
- 特定功能、类目、支付服务商或广告服务商绑定会影响变更资格。

官方接入指南还提示“确认主体信息不可变更”，而社区对个人主体能否作为变更来源存在不一致说明。因此：

- 如果未来大概率需要企业支付、商城、课程销售或行业资质，优先在注册前确定个体工商户或企业主体。
- 如果选择个人主体，应把它当作独立产品方案，不要默认后续一定能无损迁移。
- 若必须重新注册，提前考虑 AppID、历史用户、收藏、分享链接、数据和品牌入口的迁移成本。

## 8. 推荐实施路线

### 第一阶段：定位与原型

1. 写下个人 OPC 的一句话定位。
2. 列出 3—5 个代表应用或项目。
3. 确定第一版只做展示，还是同时包含真实工具能力。
4. 画出首页、应用列表、应用详情、业务、关于五个页面。
5. 用官方类目逐项核对功能。

### 第二阶段：最小可审核版本

1. 实现完整首页和至少一个可使用的核心功能。
2. 补齐应用详情、真实案例、业务说明和联系方式。
3. 完成隐私指引、空状态、错误状态和真机适配。
4. 不接支付，不聚合第三方小程序，不做未申报功能。
5. 提交审核并根据反馈修正。

### 第三阶段：发布后迭代

1. 观察用户最常查看的应用和业务。
2. 把高价值应用做成小程序内真实功能，而不只是展示卡片。
3. 每季度重新核对类目、备案、认证和支付规则。
4. 当某个独立功能形成明确用户群和差异时，再评估拆成第 2 个小程序。
